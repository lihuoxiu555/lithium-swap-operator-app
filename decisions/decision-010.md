# 决策卡片 #010

- **日期**：2026-09-16 | **阶段**：框架 MVP · 信息架构
- **项目**：运营商 APP · 底栏「消息」改为「待办」，工作台待办/警告迁入

## 决策问题

待办、警告继续占工作台顶部，还是换成底栏 Tab？原「消息」Tab 怎么处理？

## 调用的大师视角

- **乔布斯**：工作台要留给「找应用干活」。待办是另一件事，不该和宫格抢首屏。3 Tab 名额里，「待办」比「消息」更接近出门要处理的动作。
- **俞军**：现场高频是催还、退款、柜告警，不是读系统通知。把待办+警告做成独立 Tab，净价值高于消息列表。
- **张小龙**：系统消息降到「我的」二级，不刺激底栏红点；待办角标只代表「现在要处理的单」。

## 核心判断

1. 底栏改为 **工作台 / 待办 / 我的**（仍 3 Tab，替换消息，不是加第四 Tab）。
2. 工作台只留经营摘要槽 + 宫格；待办、警告整块迁入待办 Tab，左右分栏不变。
3. 待办 Tab 角标 = 待办笔数 + 警告条数。
4. 原消息列表改为 **我的 → 系统消息**。

## 反方最强论据

消息是运营通知主通道，撤出底栏会漏读。

**缓解**：我的里保留入口；正式环境若通知必须触达，用推送而不是占一个 Tab。

## Non-goals

- 不把待办做成第四 Tab
- 不改待办/警告内部流程（退款四策略、柜异常五类）
- 不把系统消息和待办队列混成一串列表

## 失效条件

- 监管要求系统公告必须在一级导航 → 再评估「我的」是否不够
- 待办+警告日均 >50 且左右分栏看不清 → 待办 Tab 改为上下两段列表

## 下一步验证

登录后工作台无待办/警告卡片 → 点底栏待办见左右两块且有角标 → 处理一笔后退回待办 Tab 而非工作台 → 我的能进系统消息。
