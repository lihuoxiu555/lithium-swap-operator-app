# 决策卡片 #002

- **日期**：2026-09-15 | **阶段**：框架 MVP → 首个业务模块
- **项目**：运营商 APP · 租赁订单

## 决策问题

工作台首个业务入口接什么？竞品截图给出「租赁订单」列表形态，是否直接按截图落地列表（含按状态差异操作）？

## 调用的大师视角

- **乔布斯（减法）**：只接一个真实模块，其余仍为 placeholder，避免一次铺开。
- **唐·诺曼（认知匹配）**：列表字段/状态/操作按截图对齐，降低运营认知迁移成本。

## 核心判断

1. 首页「经营」分组首位增加 **租赁订单**（`lease.orders`，`status: ready`）。
2. 一期原型交付：搜索（类型+扫码入口）、门店+含下级、状态 Tab、订单卡片、按状态操作按钮；操作点击仅 toast + 埋点，子页（合同/支付记录等）待详设。
3. 状态 Tab 合并截图两套导航为：待确认 / 全部 / 使用中 / 暂存中 / 已欠费 / 已结束。

## 反方最强论据

竞品两套 Tab（有/无「待确认」「全部」）可能代表不同产品版本，合并后与现网不完全一致。

**缓解**：Tab 可配置；后续与现网对齐时只改 `TABS` 配置。

## Non-goals

- 不实现结束订单/换电等真实业务逻辑与二次确认流
- 不接真实 API / 扫码硬件
- 不改 PC 后台

## 下一步验证

评审走通：工作台点「租赁订单」→ 切 Tab → 看欠费高亮与操作色块 → 返回工作台。

## 知识沉淀

ready 模块走 `openModule` 分支渲染专用页；placeholder 仍走统一占位页。
